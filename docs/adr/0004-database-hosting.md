# ADR-0004. Размещение базы данных TimeCapsule

- Статус: принято
- Дата: 2026-11-03

## Контекст

Раньше база данных PostgreSQL приложения TimeCapsule находилась на отдельном сервере AWS EC2.

При таком подходе нужно самостоятельно следить за состоянием базы, устанавливать обновления и создавать резервные копии.

Для лабораторной работы №5 нужно было выбрать другой способ размещения базы данных, чтобы упростить её обслуживание и сохранить возможность восстановления данных.

Также важно ограничить расходы на AWS.

## Решение

Для проекта выбрана Amazon RDS for PostgreSQL в одной зоне доступности (Single-AZ).

Создана база `timecapsule-dev-rds` в приватной подсети AWS. Подключаться к ней может только сервер приложения через порт 5432.

Данные перенесены со старого сервера EC2 в Amazon RDS. Приложение продолжает использовать адрес `db.timecapsule.internal`, который теперь указывает на новую базу.

В RDS включены автоматические резервные копии сроком хранения 7 дней.

Для экономии настроена автоматическая остановка базы каждый день в 23:00 через EventBridge Scheduler.

## Рассмотренные альтернативы

### 1. PostgreSQL на EC2

База данных работает на отдельном сервере EC2. Можно самостоятельно настраивать PostgreSQL, но нужно вручную заниматься обновлениями, резервными копиями и обслуживанием сервера.

Этот способ использовался раньше, но для ЛР5 был заменён на Amazon RDS.

### 2. Amazon RDS Single-AZ

База находится в одной зоне доступности. AWS помогает управлять базой, выполняет резервное копирование и обслуживание.

Этот вариант проще и дешевле, чем размещение базы в нескольких зонах. Но если зона перестанет работать, база может стать недоступной.

Этот способ выбран для проекта TimeCapsule.

### 3. Amazon RDS Multi-AZ

AWS создаёт резервный экземпляр базы в другой зоне доступности.

Если основная зона перестанет работать, AWS может автоматически переключить базу на резервный экземпляр.

Такой вариант надёжнее при отказе зоны, но стоит дороже Single-AZ. Для учебного проекта он не использовался.

### 4. Amazon Aurora

Amazon Aurora - ещё один сервис AWS для работы с базами данных, совместимый с PostgreSQL.

Он поддерживает дополнительные возможности для высокой доступности и увеличения нагрузки.

Для текущего небольшого учебного приложения эти возможности не требуются, поэтому выбран обычный Amazon RDS for PostgreSQL.

## Последствия

**Плюсы:**
- больше не нужно самостоятельно обслуживать сервер PostgreSQL на EC2;
- автоматические резервные копии хранятся 7 дней;
- можно восстановить базу на выбранный момент времени за этот период;
- база находится в приватной сети и не доступна напрямую из интернета;
- приложение продолжает использовать прежний адрес базы данных;
- автоматическая ночная остановка помогает экономить AWS-кредиты.

**Минусы:**
- Single-AZ не обеспечивает автоматическое переключение на другую зону при её отказе;
- во время остановки базы приложение не может работать с данными;
- хранение базы продолжает оплачиваться, даже когда она остановлена;
- если база остановлена 7 дней подряд, AWS автоматически запускает её;
- для важных данных возможна потеря изменений, сделанных после последней доступной точки восстановления.

**Стоимость и резервное копирование:**

В проекте используется база данных `db.t4g.micro` с хранилищем gp3 объёмом 20 ГиБ. При работе около трёх часов в день расходы составляют примерно 13–14 долларов за три месяца.

Автоматические резервные копии хранятся 7 дней. При необходимости базу можно восстановить на выбранный момент времени в пределах этого периода. Изменения, сделанные после выбранного момента, в восстановленной копии отсутствуют.

**Работа приложения и отказ зоны:**

Приложение находит базу по адресу `db.timecapsule.internal` через Amazon Route 53.

При отказе зоны `eu-central-1a` база Single-AZ может стать недоступной. Для автоматического переключения на другую зону в будущем можно использовать RDS Multi-AZ.
