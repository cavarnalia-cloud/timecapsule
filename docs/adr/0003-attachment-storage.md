
# ADR-0003. Хранение вложений TimeCapsule

- Статус: принято
- Дата: 2026-10-29

## Контекст

В ЛР2 и ЛР3 вложения пользователей TimeCapsule хранились в папке `storage/uploads` на диске EC2-сервера приложения.

Такое хранение зависит от конкретного сервера. Если сервер удалить или заменить, вложения могут быть потеряны. При запуске нескольких серверов приложения файлы также не будут автоматически доступны каждому из них.

Нужно было выбрать способ хранения вложений независимо от EC2-сервера.

## Решение

Для хранения вложений пользователей выбрано Amazon S3.

Создан бакет `timecapsule-dev-uploads-nastea` в регионе `eu-central-1`. Файлы сохраняются под префиксом `uploads/`.

Приложение работает с S3 через AWS SDK и IAM-роль `timecapsule-dev-app-role`. Для приложения разрешены операции `GetObject`, `PutObject` и `DeleteObject` только с объектами в `uploads/`.

При скачивании вложения приложение проверяет права пользователя и создаёт подписанный URL на 5 минут. Браузер получает перенаправление HTTP 302 и скачивает файл напрямую из S3.

## Рассмотренные альтернативы

### 1. Диск Amazon EBS

Вложения можно продолжать хранить на диске EC2-сервера в папке `storage/uploads`. Такой вариант простой и не требует изменения модуля хранения.

Недостаток в том, что файлы связаны с диском сервера. При замене EC2 нужно отдельно сохранять и переносить вложения. Для нескольких серверов потребуется дополнительная синхронизация или организация общего доступа.

### 2. Общая файловая система Amazon EFS

Amazon EFS позволяет нескольким EC2-серверам работать с одними и теми же файлами через общую файловую систему.

Однако необходимо настраивать сетевой доступ и подключение файловой системы к серверам. Для небольшого приложения TimeCapsule такой вариант сложнее, чем требуется.

### 3. Бакет Amazon S3

Amazon S3 хранит файлы отдельно от EC2 и позволяет работать с ними через AWS SDK.

S3 поддерживает версионирование, Lifecycle rules, IAM-политики и временные подписанные ссылки. Это позволяет сохранить вложения при замене сервера и использовать одно хранилище для нескольких экземпляров приложения.

Этот вариант был выбран для данной работы.

## Последствия

**Плюсы:**
- вложения хранятся независимо от EC2-сервера и не теряются при его замене;
- браузер скачивает файлы напрямую из S3 по подписанному URL;
- срок действия ссылки ограничен 5 минутами параметром `X-Amz-Expires=300`, а также сроком временных учётных данных;
- версионирование защищает предыдущие версии файлов от случайного удаления;
- IAM-политика не позволяет приложению окончательно удалять отдельные версии объектов;
- Lifecycle rule ограничивает рост расходов: старые версии могут переходить в Standard-IA через 30 дней и удаляться через 90 дней с сохранением двух самых новых неактуальных версий;
- когда появятся несколько серверов приложения и Load Balancer, все серверы смогут использовать один бакет S3 без синхронизации локальных вложений.

**Минусы:**
- для работы с S3 потребовалось изменить PHP-модуль хранения и установить AWS SDK;
- приложение зависит от доступности Amazon S3 и сетевого соединения;
- операции S3, хранение версий и передача данных могут создавать дополнительные расходы;
- подписанный URL доступен любому, у кого есть ссылка, до окончания срока её действия;
- при использовании нескольких серверов приложения потребуется отдельно решить вопрос общего хранения пользовательских сессий.
