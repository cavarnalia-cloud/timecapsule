# ADR-0005. Хранение пользовательских сессий TimeCapsule

- Статус: принято
- Дата: 2026-11-14

## Контекст

Раньше пользовательская сессия TimeCapsule могла храниться локально на одном EC2-сервере.

После добавления `Application Load Balancer` и `Auto Scaling Group` приложение работает сразу на нескольких EC2-серверах. Запросы одного пользователя могут попадать на разные серверы.

Поэтому сессии нужно хранить так, чтобы они были доступны всем экземплярам приложения и не зависели от конкретного EC2-сервера.

## Решение

Для хранения пользовательских сессий выбрана Amazon DynamoDB.

Создана отдельная таблица DynamoDB для сессий приложения. Все EC2-серверы Auto Scaling Group используют одну общую таблицу.

Это позволяет сохранить авторизацию пользователя даже при переключении запросов между разными серверами, а также при добавлении или удалении экземпляров Auto Scaling Group.

Для автоматического удаления устаревших сессий используется TTL.

## Рассмотренные альтернативы

### 1. Хранение сессий на EC2 со sticky sessions

`Application Load Balancer` может привязывать пользователя к одному серверу с помощью sticky sessions.

Такой вариант позволяет продолжать хранить сессию локально на EC2.

Недостаток в том, что сессия всё равно зависит от конкретного сервера. Если `Auto Scaling Group` удалит этот сервер или он станет недоступен, пользователь может потерять текущую сессию.

Поэтому этот вариант не выбран.

### 2. Хранение сессий в Amazon RDS

Сессии можно хранить в существующей PostgreSQL базе данных Amazon RDS.

В этом случае все EC2-серверы могли бы работать с одной таблицей сессий.

Недостаток в том, что каждая операция с сессией создаёт дополнительную нагрузку на основную реляционную базу данных. Для простых данных вида «ключ сессии - значение - время жизни» возможности PostgreSQL избыточны.

Поэтому этот вариант не выбран.

### 3. Хранение сессий в Amazon DynamoDB

DynamoDB позволяет хранить сессии отдельно от EC2 и основной базы данных.

Все серверы приложения используют одну таблицу, поэтому сессия доступна независимо от того, какой сервер получил запрос.

TTL позволяет автоматически удалять просроченные записи.

Этот вариант выбран для проекта TimeCapsule.

## Последствия

**Плюсы:**
- сессии не зависят от конкретного EC2-сервера;
- пользователь не теряет авторизацию при переключении между серверами;
- Auto Scaling Group может добавлять и удалять серверы без потери сессий;
- основная база RDS не используется для хранения временных сессионных данных;
- TTL автоматически удаляет устаревшие сессии.

**Минусы:**
- приложение дополнительно зависит от Amazon DynamoDB;
- необходимо настроить доступ EC2 к таблице через IAM;
- операции DynamoDB могут создавать дополнительные расходы;
- при недоступности DynamoDB работа пользовательских сессий будет нарушена.
